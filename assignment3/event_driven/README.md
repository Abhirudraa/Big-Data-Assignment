# Event-Driven File Processing on Google Cloud Platform

## 1. Project Overview

This project implements an event-driven file processing workflow using Google Cloud Platform (GCP).

Whenever a text file is uploaded to a Google Cloud Storage (GCS) bucket, a Cloud Function is automatically triggered. The function publishes the uploaded file's metadata to a common Google Cloud Pub/Sub topic.

Three independent subscribers consume the published message and perform the same processing logic:

1. A Cloud Function subscriber.
2. A Compute Engine VM subscriber.
3. A local machine subscriber.

Each subscriber retrieves the input file from GCS, identifies the longest line or lines by character length, and writes the result to a separate output location in GCS.

## 2. Architecture and Workflow

The workflow follows this sequence:

1. A text file is uploaded to the GCS input folder.
2. The GCS upload event triggers the publisher Cloud Function.
3. The publisher extracts the bucket name and uploaded object name.
4. The publisher sends the file metadata to the Pub/Sub topic `file-upload-events`.
5. Three independent subscribers receive the event through their respective Pub/Sub subscriptions.
6. Each subscriber downloads the input file from GCS.
7. Each subscriber determines the maximum line length and identifies all lines having that length.
8. Each subscriber creates a result file and uploads it to its own GCS output folder.

### Output locations

- Cloud Function: `output/cloud_function/`
- Compute Engine VM: `output/vm/`
- Local machine: `output/local/`

## 4. Processing Logic

All three main subscribers implement identical processing logic:

1. Receive the input file's bucket name and object name from Pub/Sub.
2. Download the corresponding text file from GCS.
3. Read the file line by line.
4. Calculate the character length of each line.
5. Determine the maximum line length.
6. Collect every line whose length equals the maximum.
7. Generate a result file containing:
   - Input file name
   - Maximum line length
   - All longest lines
8. Upload the result to the subscriber-specific GCS output folder.
9. Print or log the processing details.

The logic supports multiple lines sharing the same maximum character length.

## 5. GCP Resources

The workflow uses the following resources:

- Google Cloud Storage bucket for input and output files.
- Cloud Storage event trigger through Eventarc.
- Publisher Cloud Function.
- Pub/Sub topic: `file-upload-events`.
- Independent Pub/Sub subscriptions for the subscribers.
- Subscriber Cloud Function.
- Google Compute Engine VM.
- Local Python environment with Google Cloud authentication.

## 6. Dependencies and Execution

Install the subscriber dependencies using:

```bash
pip install -r requirements-subscribers.txt
```

The publisher and Cloud Function subscriber dependencies are specified separately in their respective `requirements.txt` files.

The subscriber scripts require appropriate Google Cloud authentication and Pub/Sub subscription access. The GCP resources and project configuration must also be available.

## 7. Expected Result

Each subscriber independently generates a result file in its respective GCS output folder.

The output identifies the source file, maximum line length, and all lines matching that maximum.

The three output files can be compared to verify that all subscribers perform the same processing logic.

## 9. Conclusion

This project demonstrates an event-driven architecture on Google Cloud Platform using Cloud Storage, Cloud Functions, Eventarc, Pub/Sub, and Compute Engine.

A single file upload initiates processing by multiple independent subscribers. Each subscriber retrieves the same input file, performs the longest-line analysis, and stores its result separately in GCS.
